## 一、一句话

**让知乎上任何一个答主，先替你把这个问题答一遍。**

用户提出一个真实问题，指定想听谁回答 —— 哪怕这位答主从没答过这个问题。
看山按这位答主的**领域、立场和说话方式**（由他本人的公开回答蒸馏而来）生成一份分身回答，
再标出这几位答主**共同缺失的那一块**，把缺口交给真实的人接管。
虚拟回答负责把问题问清楚，真人负责给出只有亲身经历才能给出的答案。

**评价标准是「像这个人」>「答案完美」**：同一个问题换三位答主，遮住名字也该看得出不是同一个人写的。

**赛道**：知识炼金场｜社区 × 学习（与灵魂匹配局交叉）

## 二、问题与目标用户

### 真实问题

知乎上同一个问题往往有几十个高质量回答，观点互相冲突。但用户看到的是**排序**，不是**结构**——
没有人告诉他这些回答在争什么、分歧点在哪、以及**他们共同没有回答的是什么**。

同时，AI 的回答很快但缺一手经验，真人的回答可信但慢。中间缺的是把两者接起来的那一步。

### 目标用户

| 用户 | 场景 | 他要什么 |
|---|---|---|
| **提问者**（主） | 转行、择校、选品、看病、育儿、创业等真实决策 | 不是标准答案，而是「有哪些立场、各自代价是什么、我还缺什么信息」 |
| **有经验的人**（副） | 在某个领域真的踩过坑 | 被问到一个「正好是我能答」的好问题，而不是泛泛求助 |
| 社区 | 知乎内容生态 | 更少重复提问、更多有信息增量的回答 |

### 核心洞察

**问题的提法，决定了能不能把经验钓出来。**
所以产品不是「AI 帮你答」，而是「AI 帮你把问题问对，然后找到那个能答的人」。

## 三、核心体验（一条闭环，Demo 完整走通）

```
① 提问   输入真实问题 / 粘贴知乎问题链接 / 从热榜挑一个
② 选人   ★ 指定想听谁回答（多选）；也可以交给看山按问题推荐
③ 证据   每位答主用领域关键词检索知乎真实回答，带作者和链接
④ 作答   基于证据、按该答主的 voice 生成回答（字数区间也由人格决定）
⑤ 加人   继续邀请新答主加入，只生成这一位，不重跑已有分身
⑥ 互怼   一轮互相回应：找出最尖锐的分歧，让双方各回一段
⑦ 缺口   ★ 系统指出所有回答共同缺失的那一块，以及为什么这是缺口
⑧ 派单   缺口 → 需要什么样的真人 → 候选真人（来自真实来源作者）
⑨ 接管   真人补充 → 标记为「真人补充」→ 并入最终稿
⑩ 带走   整理成带来源归属的正文，用户自己发布到知乎
```

**第 ② 步与第 ⑦ 步是本作品的两个创新点。**
第 ② 步：不是让 AI 换六种语气，而是让**具体的人**各自作答 —— 这需要真实的人格蒸馏。
第 ⑦ 步：市面上的多 Agent 产品做到第 ④ 步就结束了；
「一群分身各自答完，系统指出它们共同的盲区」这件事，只有把多个人格放在一起比较才能做到。

## 四、技术方案

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Next.js 14 App Router + React 18 | 页面与服务端代理同仓 |
| 语言 | TypeScript（strict） | 上游响应全部显式建模 |
| 动效 | Motion（`motion/react`） | 弹簧驱动；看山角色引擎 |
| 样式 | 手写 CSS + 设计 token | 深色舞台 + 四色状态系统 |
| 校验 | Zod | route handler 入参 |
| 数据 | 浏览器 localStorage | P0 无需数据库，刷新不丢当前镜像 |
| 部署 | 自托管（Node.js 常驻进程） | 公网 HTTPS `zhihu.cauai.fun` |

### 架构要点

- **凭证隔离**：`lib/zhihu/` 标注 `server-only`，Access Secret 只存在服务端环境变量，
  编译期即阻止其进入客户端 bundle。
- **额度保护**：所有上游调用经过进程内 TTL 缓存 + 同请求去重。
  平台实际发放：知乎搜索 / 全网搜索 / 直答各 5000 次/天，热榜与问题回答摘要各 100 次/天
  （`GET /api/zhihu/quota` 可当场核验）。**本产品在此之上自限：热榜与直答按 100 次/天
  做预算**，把它们当低额度能力对待 —— 自限比平台给的更严，留出余量。
  同一个问题重复演示不再消耗额度。
- **上游串行闸门**：内容检索类接口在并发时会被上游限流，因此强制排成一条队列并保持最小间隔；
  直答实测可并发，走 2 路并发池 + 线性退避重试。
- **纯函数业务层**：路由与缺口识别放在 `lib/domain/`，无 IO，可测试、可复现、零额度消耗。
- **降级完备**：未配置凭证 / 鉴权失败 / 额度耗尽 / 空结果 / 超时，都有真实提示，
  **不用假数据填充**。直答失败时降级为「基于检索的摘要」并在页面明确标注 `generatedBy`。

### 答主人格从哪来（数据管线）

预置 **16 位**跨领域、风格反差最大的真实答主：
半佛仙人 / 张佳玮 / 贱贱 / 李松蔚 / 大猛 / 陈章鱼 / 马前卒 / 太空精酿 /
李雷 / 温义飞 / 采铜 / 动机在杭州 / 丙等星 / 蒋校长 / 赤戟 / 陈兰香。
（2026-09-15 从 6 位扩到 16 位：原 6 位集中在互联网 / 心理 / 制造 / 文学，
换个领域的问题就容易全打平；新增 10 位把工业、航天、生物、金融、学习方法、
心理咨询、半导体、军事史、网文、法律补齐。）

其中 **15 位**由**本人公开回答蒸馏**（每人 28–30 条，共 448 条，见各自人格文件的
`corpus.sampleSize`）；**蒋校长（`jiangxiaozhang`）是唯一一位预置人格** ——
检索不到他本人署名的可用公开回答，故 `corpus.real=false`、`sampleSize=0`，
不列出任何来源条目，也不挂「基于公开片段提取」标识。**不把预置内容伪装成真实蒸馏的语料。**

抽四要素：知道什么（`knows`）、怎么看问题（`stance`）、
怎么说话（`voice`，含句长/语气/口头禅/情绪强度/字数区间）、明确不装懂的范围（`doesNotKnow`）。

- 抓取脚本 `scripts/persona-crawler.mjs`：只保留作者本人的回答，原始语料写入已 gitignore 的目录，**不入公开仓库**。
- 蒸馏脚本 `scripts/distill-personas.mjs`：把原始回答喂给直答，产出 `lib/domain/personas/<handle>.ts`。
- 人格文件**只存特征与短引用**，不存大段原文。
- **不在卡片上挂「未验证」类标签**（2026-09-15 已全部移除：那类自述读起来像免责声明
  而不是身份说明）。诚实性改由**答主档案页正文**承担，且随语料状态自动切换：
  已蒸馏的标「N 条有效样本 · 真实抓取 + 时间」并列出代表性来源；
  未抓取的蒋校长标「公开印象档案」，明说不声称「真实蒸馏」，且不列出任何来源。
- 用户临时指定一位**没预置**的答主时，走在线蒸馏：搜索 → 只留他本人写的内容 → 抽四要素，
  **如实返回命中条数**；命中 0 条时标注低置信度，不假装成功。

### 看山角色引擎

参考 `blessonism/grok-icon-study` 的**架构思路**（表驱动状态机 + 停留时长区间 + 弹簧过渡），
为刘看山**原创定义** 10 个状态、眼神目标表与姿态表，全部几何与配色自绘。

看山不是装饰，而是**流程主持人**：接入 → 路由 → 检索 → 比对 → 作答 → 发现缺口 → 邀请真人 → 补充已写入，
状态与产品步骤一一对应（`components/kanshan/states.ts` 的 `flowStateAt()` 是唯一状态源）。
动效由 Motion 的 `useSpring` / `useTransform` / `useAnimationFrame` 驱动，
指针跟随写入 MotionValue，不触发 React 重渲染；`prefers-reduced-motion` 时关闭随机切换与跟随。

## 五、用到了哪些知乎开放能力

| 能力 | 接口 | 用途 |
|---|---|---|
| 知乎搜索 | `GET /api/v1/content/zhihu_search` | 每位答主取回真实回答作为证据；也是临时答主在线蒸馏的检索源 |
| 全网搜索 | `GET /api/v1/content/global_search` | 补充站外权威来源做对照 |
| 知乎热榜 | `GET /api/v1/content/hot_list` | 一键从真实热点进入体验 |
| 问题回答摘要 | `GET /api/v1/content/question_answers` | 粘贴知乎问题链接时读取真实回答 |
| 知乎直答 | `POST /v1/chat/completions` | 按该答主的人格（voice）生成回答；也用于抽取人格四要素与互相回应 |
| 问题推荐 | `GET /api/v1/user/question_recommendations` | 从真实用户画像找「该被问的人」 |
| 额度查询 | `GET /api/v1/quota` | 页面显示剩余额度，避免演示中途耗尽 |
| 知乎登录（OAuth） | `openapi.zhihu.com/authorize` | 登录能力预留，凭证到位后启用 |

### 三条如实说明的边界

1. **平台没有发布接口。** 全量审计 54 个文档条目，均为只读或与发布无关。
   因此本产品**不承诺一键发布**，也没有「预填」按钮：只把整理好的正文（含来源归属）放进可复制面板，
   同时给出知乎真实编辑器深链，由用户自己粘贴发布。代码里 `canPublishViaApi: false` 是硬编码事实。
2. **站内黑客松内容接口当前不可用。** 官方指南提到的
   `api.zhihu.com/km-indep-home/hackathon/v2/{story,knowledge}/list` 依赖浏览器登录票据，
   服务端直连返回 401。已接入封装，页面如实标注为不可用，不替换成别的数据假装可用。
3. **参数名踩坑已记录。** 搜索类接口的条数参数是 `Count` 而不是 `Limit`；
   传错不报错，只静默按默认值返回 10 条。已按官方字段名修正并写入审计文档。

## 六、与知乎生态的契合点

1. **证据回流**：每条分身回答都带真实的知乎链接与作者名，用户顺着链接回到知乎阅读原文。
2. **激活沉默的分享者**：缺口派单指向真实知乎用户，把「愿意分享但没被问对」的人重新激活。
3. **减少重复提问**：先让 AI 把问题问清楚，用户带回去的是更有信息增量的问题。
4. **提升回答质量**：真人只回答他真正擅长的那一块，而不是被泛泛的问题劝退。
5. **合规优先**：不刷量、不批量调用；所有内容保留归属；凭证严格留在服务端。
   预置答主的人格语料为**本地一次性取样**（脚本与原始语料均不入公开仓库），人格文件只存特征与短引用。

**知乎在这个产品里不是数据源，而是循环本身。**

## 七、对社区用户的实际价值

| 对象 | 价值 |
|---|---|
| 提问者 | 从「看排序」升级为「看结构」：知道有哪些立场、各自代价、以及自己还缺什么信息 |
| 有经验的人 | 被问到一个「正好是我能答」的问题，而不是泛泛求助 |
| 知乎平台 | 更多有信息增量的回答，更少重复提问；内容带来源回流 |
| 社区生态 | 把 AI 的效率与真人的可信度接起来，而不是用 AI 替代真人 |
