# 分支与队列规则

> 2026-09-15 立。角色分工见 [`collaboration.md`](collaboration.md)（二线程模型）。
> 这份文件只讲一件事：**队列**。为什么它是本仓库最贵的瓶颈，以及怎么把成本压下去。

---

## 一、问题：一个会自我加速的正反馈环

`main` 开了分支保护 `strict: true`（**分支必须与 main 同步才能合**）。于是：

```
每合并 1 个 PR  →  其余所有在途 PR 全部失效  →  必须各自 rebase
队列长度 N      →  每合 1 个产生 N-1 次返工
```

审计/上线线程是**单点**，一个人干「审代码 + rebase + build + 合并 + 部署 + 线上复验」六件事。
其中 **rebase 是被动产生的、随队列长度线性增长的无效功** —— 越忙越慢，越慢积压越多。

**实测（2026-09-15 12:00 前后）**：

| 信号 | 实测值 |
|---|---|
| 排队时长趋势 | 1 → 8 → 2 → 14 → 23 → 32 → 43 → **88** 分钟（单调上升） |
| 80 分钟内 | 新建 **8** 个 PR，只消化 **5** 个 |
| 一度积压 | **6** 个在途，其中 **5** 个已冲突 |
| 部署本身 | 不慢：#9 合并到线上生效约 **17 分钟** |

**结论：这不是「审计线程不够努力」，是队列太长。要治「进入」，不是治「努力」。**
也不要靠「再加一条线程」解决 —— `collaboration.md` 已记录过「多线程的协调成本超过并行收益」。

## 二、四条规则

### 规则一：在途 PR ≤ 2

同一时间最多允许 2 个 open PR。超过就先清空再开新分支。

为什么是 2 而不是 1：留 1 个名额给「发现线上问题要立刻修」这类插队项；
超过 2 个之后，每次合并的返工次数开始超过 1，收益立刻变负。

**在途满 2 个时，新工作请先写在本地分支上，不要开 PR。**

### 规则二：rebase 责任在开发线程，不在审计线程

提 PR **之前**自己同步到最新 main 并跑合并预检：

```bash
git fetch origin main
git rebase origin/main              # 本机 rebase 偶发失败时改用 git cherry-pick <sha>
node scripts/verify-merge.mjs <本分支>   # 退出码 0 才算就绪
```

审计线程只做「审 + 合 + 部」。**把 rebase 留给审计线程，等于把最贵的活压在最窄的瓶颈上。**

### 规则三：提 PR 前 5 秒查重

```bash
node scripts/pr-queue.mjs
```

它会列出在途 PR、冲突状态、排队时长，以及**两两之间的文件重叠**。
重叠 ≥3 个文件 ≈ 同一件事的两个版本 —— 本仓库已经发生过一次（PR #9 与 #12 各自独立做了
同一个信息架构重构，改同一批 7 个文件，只能合一个）。

**冲突矩阵只能告诉你「它们冲突」，不能告诉你「它们不该同时存在」。查重靠这一条命令。**

### 规则四：队列满时先清空，不要排队

队列已满时，正确的动作是**帮审计线程把在途的清掉**（催 rebase、关掉已被取代的分支），
而不是把自己的 PR 也排进去。少一个冲突 PR = 审计队列少一份无效功。

自己那条**已被他人 PR 取代**的分支，主动关掉并在关闭说明里写清「哪一部分仍然有效」，
比留着让对方去判断便宜得多。

## 三、一键操作

| 想做什么 | 命令 |
|---|---|
| 体检队列（提交前必跑） | `node scripts/pr-queue.mjs` |
| 机器可读（脚本里用） | `node scripts/pr-queue.mjs --json` |
| 批量把在途 PR 同步到最新 main | Actions → **同步在途 PR 分支** → Run workflow |
| 合并预检 | `node scripts/verify-merge.mjs <本分支>` |
| 部署 | 见下节 |

**「同步在途 PR 分支」为什么是手动触发**：自动在每次 push 后强推别人正在开发的分支，
会和开发者本地的 push 打架（本仓库已丢过一次 25 个文件的未提交改动）。
同步应由审计线程在准备合并前主动发起。它有 `dry_run` 开关，可以先看再动。

## 四、部署（现有形态，无需改动）

```bash
cd /opt/no2zhihu
git config --global --add safe.directory /opt/no2zhihu
ps aux | grep 'next build' | grep -v grep          # 有输出 = 并发构建，停手等
git reset --hard origin/main
su - no2zhihu -s /bin/bash -c 'cd /opt/no2zhihu && npm run build'
systemctl restart no2zhihu
```

判成败看 `✓ Compiled successfully`，别只看 exit code。服务器是多站点共用机
（同机还有 `ans.cauai.fun` / `sub2api` / `omniroute`），**不要动它们的 nginx 与 systemd**。

> **合并后自动部署**需要仓库 Secrets 里配好部署用的 SSH key 与主机地址；
> 配置之前不要加自动触发的 workflow，否则会得到一个必然失败的红叉。
> 配好之后再加 `deploy.yml`（`workflow_dispatch` + `push: main`）即可。

## 五、这套规则生效的判据

一周后回看这几个数，任一项恶化说明规则没被执行：

- 在途 PR 数 **始终 ≤ 2**
- 最老在途 PR 的排队时长 **< 15 分钟**
- 在途 PR 里 `dirty`（需返工）的比例 **= 0**
- 「新建 : 合并」的比值 **≈ 1 : 1**
