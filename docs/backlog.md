# 需求台账（Backlog）

> **这是「owner 提过的要求」与「提出的问题」的唯一台账。**
> 与 `roadmap.md`（任务分解）、`threads/`（谁在做）的分工见文末。
> 最后更新：2026-09-16（17:15 · A1/A2 部分上线、D1 已上线）

## 为什么需要它

2026-09-16 owner 问「我给过开发线程的问题，有没有存到一个特定区域？」——实查结论：**没有**。
owner 的反馈此前散落在三处，每处都不适合当台账：

| 曾记在哪 | 为什么不合适 |
|---|---|
| `docs/threads/audit.md` 的一节 | 按设计「超 24 小时可删」，且开发线程按约定只看自己的文件 |
| `roadmap.md` / `acceptance.md` | 它们是**代码完成度**，不是「owner 要什么」；且已停在 09-14 |
| 本地记忆 / 对话 | 换机器就断，开发线程看不到 |

后果是真实的：owner 在 09-15 提的「广场观感不够顶级 / 能动么」，
**中间有一段时间处于「提过但没人接手」的状态**，直到 #77 才被认领。

## 用法（三条硬规矩）

1. **owner 提要求 → 先落这里再开工。** 不许只写在 PR 描述或对话里。
2. **PR 合并时回来改状态。** 状态只有四档：`待认领` / `在做` / `已上线` / `不做（附理由）`。
3. **每条必须能追溯到证据** —— owner 的原话、PR 号、或线上实测，不写「据说」。

## 与其它文档的分工（互补，不重复）

| 文档 | 回答的问题 | 时点 |
|---|---|---|
| **`backlog.md`（本文件）** | **owner 要什么、做完没有** | 长期 |
| `roadmap.md` | 代码层面还剩哪些任务、优先级 | 里程碑 |
| `acceptance.md` | 验收项逐条是否通过 | 交付前 |
| `threads/` | **谁**在做、正在改哪些文件 | 开工时（短效，24h） |
| `prd.md` / `architecture.md` | 产品与技术事实 | 长期 |

## 维护

- **谁改**：任何线程都可以改（改状态时在 PR 里说明依据）。
- **什么时候改**：① owner 提新要求时；② 一个 PR 合并后回头改它对应的行。
- **不许做**：把「待认领」悄悄删掉 —— 要么改成 `已上线`（附 PR 号），要么改成 `不做`（附理由）。
