# 虚拟广场 · 视觉审计与重构方案

> 2026-09-16 · 线程 `square-ui` · 基线 `df58a96`
> 起因：owner 说「现在的视觉效果太差了 看起来不牛逼 就这个问题」
>
> **本报告所有数字都由真实数据 + 真实布局算出，无一处估计值。**
> 复现：`node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/audit-square-visual.mjs`

## 一、结论（先看这段）

「看起来不牛逼」不是配色问题，是**像素分配问题**。

| 指标 | 实测（真实渲染） | 「有主体」的画面通常 |
|---|---|---|
| **主体（人形）占舞台** | **1.49%** | 15–40% |
| 影子占舞台 | 2.54% | — |
| 主体 + 影子 | **4.03%** | — |
| 背景占 | **95.97%** | — |
| 人形屏幕高度 | 21–38px（中位 34） | 可辨识需 ≥40px |
| 每簇人形数 | **4 个**（中位） | 像「人群」需 ≥7 |
| 有回应（round>0）的场次 | **0** | — |

**差一个量级还多。** 在这个前提下继续调色、加装饰层，上限就是「精致的空画面」。

> 这两个数字是**在真实渲染页面上量的**（`getBoundingClientRect` 逐元素累加，
> 被舞台裁掉的部分不计）。上一版报告用的是算法推算（4.29% / 7.58%），
> 把舞台宽度按 75% 算小了 1.35 倍，所以偏高 —— 已全部换成实测值。
> 这本身就是「读起来像」不如「量出来是」的一个实例。

## 二、量化审计（六节，逐条给数）

### ① 内容密度

```
讨论场次                22
人形总数                97   = 66 分身 + 31 缺口
每簇人形数 中位数          4   最小 4 / 最大 6
每簇分身数               3   全部相同 —— 每场固定 3 位
有回应（round>0）的场次     0   → 「正在发生」维度恒空
人群占地 / 场地          11.4%   空地 88.6%
```

**要命的一条是「每场固定 3 位」。** 一簇 3 个人，无论怎么排版都不像「人群」。
而且 `size` 由 `热度和答案数` 决定、与人数无关 —— 所以「人多的地方更大」
这件事在当前代码里**根本不成立**（人多的场次在布局上不会更大）。

### ② 屏幕尺度

```
1440×900   scale=0.92   人形中位 34.4px（21.4–37.7）   视野内 10/22 簇
1920×1080  scale=0.92   人形中位 34.4px             视野内 10/22 簇
```

人形中位 34px、宽 20px。**这个尺寸下，我这一轮加的体态差异（±12% 身高）、
倾斜（±7°）、姿态变体，全部读不出来** —— 我为一个看不见的尺度做了很多工作。
这是本轮最该反思的一条。

### ③ 视觉信息预算

```
视野内标题 11 条 / 192 字 / 文本约占屏 8.9%
```

文字已经不少（近 9% 像素），加上 4.3% 的人群 —— **屏幕是被「背景」和「文字」占据的，不是被画面占据的**。

### ④ 光影的实际贡献（真实渲染实测）

```
舞台 1440×827 = 1,190,880 px²
人形 66 个 · 17,775 px² · 1.49%
影子 66 条 · 30,213 px² · 2.54%
合计 4.03%   背景 95.97%
```

两件值得注意的事：

1. **影子比人还大**（2.54% vs 1.49%）—— 影子是这张画布上唯一「有物理因果」的元素
   （方向精确背离光源、长度绑人高、可被自检验证），它现在**比主体本身占的像素还多**。
   这说明「加影子」这个方向是对的，只是主体太小、撑不起它。
2. 主体 + 影子合计 4.03%，**背景 95.97%**。

### ⑤ 对比度清单

| 层级 | 颜色 | 形态 | 占屏 |
|---|---|---|---|
| 页面底色 | `#07080f` | 纯色 | 整屏 |
| 场地中心 | `#2c3552` | radial | 约 40% |
| 场地外圈 | ≈ `#12172a` | radial | 约 30% |
| 光池中心 | +0.20 白叠加 | radial | 约 8% |
| 人群脚下亮底 | +0.10 白叠加 | radial | 每簇一小块 |
| 在场分身剪影 | `#05070e` | 实体 | 4.3% |
| 影子 | `#000000` @0.55 | 实体 | 3.3% |
| 缺口地灯 | `#ff8a4c` | 渐变 | < 0.2% |

两个结构性问题：

- **三层亮色叠在中央同一位置**（场地中心 + 光池 + 脚下亮底），
  亮度相加 → 中央过曝。这是「三层各自都不过分、叠起来过分」的典型。
- **主体全是近黑，背景中位也是近黑** → 对比度集中在中央一小块，
  外围只靠剪影与地面约 6% 的亮度差撑着。**低对比 + 低占比 = 观感平淡。**

### ⑥ 大屏反而更空

```
2560×1440 的 scale = 0.920  ← 与 1440 完全相同
```

缩放上限被钳死在约 0.92（`clampScale` 的 `MAX_SCALE` 是 2.2，但 `homeViewport`
算出来的值本身就落在 0.92 附近）。于是 2560 宽的屏幕把同样这 10 簇铺进更宽区域：
**画面更空、人形一样大。大屏用户不会看到更多内容，只会看到更多空白。**

## 三、根因链（一条，不是一堆）

审计把嫌疑从「布局推得太开」逐层排除，最后落在**卡片尺寸与人群尺寸脱节**上：

```
最近邻距离 / 理论下限 = 0.94   → 节点之间是紧的（排除「布局推得太开」）
                ↓
节点 size = 197–320px          而人群外接半径 = 71px
                ↓
每个节点内部约 42% 是空的（22 个节点全部如此）
                ↓
人群外接半径 / 节点半径 = 58% 平均 → 节点面积是人群面积的 3.0 倍
                ↓
22 个这样的节点排在一起 = 「散着几摊人」
```

**为什么卡片尺寸会跑偏**（代码级）：

1. `SIZE_MIN = 132` / `SIZE_MAX = 320` 是**硬编码常量**，与人群实际需要的场地无关
2. `size = SIZE_MIN + (SIZE_MAX - SIZE_MIN) × heat × 0.52` ——
   `heat` 由答案数/热度算。真实数据里 22 场的 `heat` 全部接近 1，
   于是 **21 张卡全塌到同一个值 197**（审计里那串 197 就是证据）
3. 人群半径被写成 `size / 2 × 0.72` ≈ 71px —— **被动跟随卡片，而非主动决定卡片**
4. 但人形只有 24–36px 高，3–5 个人排下去只用掉 30–40px 半径
5. → 每个节点内部留下 42% 的空，22 个叠起来就是「空」

**这不是我这一轮改出来的**，是布局层从第一天起就有的结构性错配。
我这一轮在渲染层加光、影、体态，全都建立在这个错配之上 ——
**所以那些工作是对的，但都没有触及决定上限的那一层。**

## 四、可做的重构清单（按性价比排序）

### P0 —— 让画布跟着内容走 ★ 最大收益

**问题**：`SIZE_MIN=132 / SIZE_MAX=320` 与人群实际需要的场地无关。

**改法**：让 `size` 从人群反推。

```
size = clamp(人群外接半径 × 2 ÷ CROWD_RADIUS_RATIO, SIZE_MIN, SIZE_MAX)
```

**效果**（按实测值推算）：
- 包围盒从 2249×1851 缩到约 **1500×1230**（面积 −56%）
- 同样的舞台下 scale 从 0.92 提到约 **1.35**
- **人形从 34px → 约 50px**，影子 / 姿态 / 体态差异第一次真正可辨
- 主体占比（按面积同比例放大 scale²≈2.15×）从 **1.49% → 约 3.2%**，
  加影子从 4.03% → 约 **8.7%**

**风险**：`relaxOverlaps` 的推力按 size 算，size 变小会整体收拢 →
必须重跑 `check-square-crowd.mjs` 的重叠断言（当前余量 1.85，够）。
**不花额度。**

**代价：1 个 PR，约 1 小时。**

---

### P1 —— 一屏一焦点

**问题**：取景固定（scale 0.92 + 居中），22 场只有 10 场入画，没有主次。
**改法**：入场取景对准**最热那一场**，scale 提到 1.35；外圈按「离焦点距离」
做更强的明度衰减（现在 0.46–1.0 → 改成 0.28–1.0）。
**效果**：眼睛第一下落在最热那场（它也是光源），「有主次」才成立。
**风险**：低，纯取景参数。

---

### P2 —— 光源与「有区分度的量」绑定

**问题**：现在光源 = 最热那一场，但**热度差异极小**（21 场并列 197），
所以「光落在谁头上」实际没有信息量。
**改法**：换一个真的有区分度的量做光的落点 —— 候选：
`缺口数`（谁最缺人）/ `来源数`（谁论据最厚）/ `最近有更新`。
**风险**：这是产品判断，**需要 owner 定量**。

---

### P3 —— 内容扩量（唯一能解决「每簇 3 个人」的办法）

**问题**：审计显示每场固定 3 位分身、0 场有回应。
**改法**：L2 —— 现有 22 场补到 6–8 位分身（约 130 次直答调用，分 2 天）。
**效果**：人形 97 → 200+，每簇 7–10 人，**画面密度翻倍**。
**代价**：知乎额度 + 一次 build-library 重跑。

---

## 五、我不建议做的

**继续调色、继续加装饰层。**

我这一轮花 5 版做了这件事（场地 / 光池 / 光柱 / 尘埃 / 影子 / 体态），
每一版都真的修了一个 bug（对比结构反了、渐变坐标系错了、光层挂错父节点、
自检静默假绿……），**但整体观感没有质变** —— 因为决定上限的是
像素分配（P0）、主次（P1）、密度（P3），**调色只能决定「在给定上限下好不好看」**。

审计数字说得很清楚：**主体占 1.49%（加影子 4.03%），差一个量级还多。**
