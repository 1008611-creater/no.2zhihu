## 作品名：二号知乎（Human Mesh）

**赛道**：知识炼金场｜社区 × 学习（与灵魂匹配局交叉）

**一句话**：让知乎上任何一个答主，先替你把这个问题答一遍——哪怕他从没答过。
看山按这位答主的领域、立场和说话方式生成分身回答，再指出这几位**共同的盲区**，把那一块交给真实的人。
评价标准是「像这个人」>「答案完美」。

---

## 1. 核心创作思路与目标用户

### 真实问题

在知乎上，一个真实的问题往往有几十个高质量回答，观点互相冲突。但用户看到的是**排序**，
不是**结构**：没人告诉他这些回答到底在争什么、分歧点在哪、以及**他们共同没有回答的是什么**。

同时，AI 的回答很快但缺一手经验；真人的回答可信但慢。中间缺的是把两者接起来的那一步。

### 目标用户

- **主要**：正在做真实决策的人——转行、择校、选品、育儿、创业。他要的不是标准答案，
  而是「有哪些立场、各自的代价是什么、我还缺什么信息」。
- **次要**：在某个领域真的踩过坑、愿意分享的人。他们不会主动回答泛泛的求助，
  但会被一个「正好是我能答」的好问题激活。

### 核心洞察

**问题的提法决定了能不能把经验钓出来。** 所以产品不是「AI 帮你答」，
而是「AI 帮你把问题问对，然后找到那个能答的人」。

## 2. 用户如何完成核心体验

```
① 提问   输入真实问题 / 粘贴知乎问题链接 / 从热榜挑一个
② 选人   ★ 指定想听谁回答（多选）；也可以交给看山按问题推荐
③ 证据   每位答主用领域关键词检索知乎真实回答，带作者和链接
④ 作答   基于证据、按该答主的 voice 生成回答（字数区间也由人格决定）
⑤ 加人   继续邀请新答主加入，只生成这一位，不重跑已有分身
⑥ 互怼   一轮互相回应：找出最尖锐的分歧，让双方各回一段
⑦ 缺口   ★ 系统指出所有回答共同缺失的那一块，以及为什么这是缺口
⑧ 派单   缺口 → 需要什么样的真人 → 候选真人
⑨ 接管   真人补充 → 标记为「真人补充」→ 并入最终稿
⑩ 带走   复制为知乎回答格式，用户自己发布到知乎
```

**一次完整体验约 60–90 秒**，适合评委在 3 分钟内看懂。

**两个创新点**：第 ② 步——不是让 AI 换六种语气，而是让**具体的人**各自作答；
第 ⑦ 步——「一群分身各自答完之后，系统指出它们共同的盲区」，
这件事只有把多个人格放在一起比较才能做到。

## 3. 整体技术方案

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Next.js 14 App Router + React 18 | 页面与服务端代理同仓 |
| 语言 | TypeScript（strict） | 上游响应全部显式建模 |
| 动效 | Motion（`motion/react`） | 弹簧驱动；看山角色引擎 |
| 样式 | 手写 CSS + 设计 token | 深色舞台 + 四色状态系统 |
| 校验 | Zod | route handler 入参 |
| 部署 | 自托管（Node runtime） | 公网 HTTPS `zhihu.cauai.fun` |

### 架构要点

- **凭证隔离**：`lib/zhihu/` 标注 `server-only`，Access Secret 只存在服务端环境变量，
  编译期即阻止其进入客户端 bundle。
- **额度保护**：所有上游调用经过进程内 TTL 缓存 + 同请求去重。
  平台实际发放：知乎搜索 / 全网搜索 / 直答各 5000 次/天，热榜与问题回答摘要各 100 次/天
  （`GET /api/zhihu/quota` 可当场核验）。**本产品在此之上自限：热榜与直答按 100 次/天
  做预算**，把它们当低额度能力对待 —— 自限比平台给的更严，留出余量。
- **纯函数业务层**：路由与缺口识别放在 `lib/domain/`，无 IO，可测试、可复现、零额度消耗。
- **降级完备**：未配置凭证 / 鉴权失败 / 额度耗尽 / 空结果 / 超时，都有真实提示，
  不用假数据填充。

### 答主人格从哪来（数据管线）

**16 位**跨领域、风格反差最大的真实答主（15 位人格由本人公开回答蒸馏，1 位预置）：
半佛仙人 / 张佳玮 / 贱贱 / 李松蔚 / 大猛 / 陈章鱼 / 马前卒 / 太空精酿 /
李雷 / 温义飞 / 采铜 / 动机在杭州 / 丙等星 / 蒋校长 / 赤戟 / 陈兰香。

（2026-09-15 从 6 位扩到 16 位：原 6 位集中在互联网 / 心理 / 制造 / 文学，
换个领域的问题就容易全打平；新增 10 位把工业、航天、生物、金融、学习方法、
心理咨询、半导体、军事史、网文、法律补齐，保证任何一类问题都有对口的人。）

其中 **15 位**的人格由**本人公开回答蒸馏**：每人 28–30 条真实回答，共 448 条，
条数写在各自的 `lib/domain/personas/<handle>.ts` 里（`corpus.sampleSize`），可逐位核对。
**蒋校长（`jiangxiaozhang`）是唯一一位预置人格** —— 检索不到他本人署名的可用公开回答，
因此他的 `corpus.real=false`、`sampleSize=0`、来源列表为空；
档案页与卡片上都不挂「基于公开片段提取」标识，也不列出任何来源条目，
**不把预置内容伪装成真实蒸馏的语料**。

抽四要素：`knows`（知道什么）、`stance`（怎么看问题）、
`voice`（怎么说话：句长/语气/口头禅/情绪强度/字数区间）、`doesNotKnow`（明确不装懂的范围）。

- 抓取脚本 `scripts/persona-crawler.mjs`：只保留作者本人的回答，原始语料写入已 gitignore 的目录，**不入公开仓库**。
- 蒸馏脚本 `scripts/distill-personas.mjs`：产出 `lib/domain/personas/<handle>.ts`，**只存特征与短引用**。
- **不在卡片上挂「未验证」类标签。** 那类自述（「预置人格 · 未抓取全量回答」）读起来像免责声明，
  而不是身份说明，已于 2026-09-15 全部移除，也不替换成任何中性说法。
  诚实性改由**答主档案页正文**承担，且随语料状态自动切换：已蒸馏的 15 位标注
  「蒸馏依据 · 基于公开片段提取 · N 条有效样本 · 真实抓取 + 抓取时间」并列出代表性来源；
  未抓取的蒋校长标注「公开印象档案」，明说没有抓取全量回答、不声称「真实蒸馏」，
  且不列出任何「来源」条目，避免把预置内容伪装成真实语料。
- 用户临时指定一位**没预置**的答主时，走在线蒸馏，**如实返回命中条数**；命中 0 条时标注低置信度。

### 看山角色引擎

参考 `grok-icon-study` 的**架构思路**（表驱动状态机 + 停留时长区间 + 弹簧过渡），
为刘看山**原创定义** 10 个状态、眼神目标表与姿态表，全部几何与配色自绘。
看山不是装饰，而是**流程主持人**：接入 → 路由 → 检索 → 比对 → 作答 → 发现缺口 → 邀请真人 → 补充已写入，
状态与产品步骤一一对应（`components/kanshan/states.ts` 的 `FLOW_STATES`）。
动效由 Motion 的 `useSpring` / `useTransform` / `useAnimationFrame` 驱动，
指针跟随写入 MotionValue，不触发 React 重渲染；`prefers-reduced-motion` 时关闭随机切换与跟随。

## 4. 使用了哪些知乎开放能力

| 能力 | 接口 | 用途 |
|---|---|---|
| 知乎搜索 | `GET /api/v1/content/zhihu_search` | 每位答主取回真实回答作为证据；也是临时答主在线蒸馏的检索源 |
| 全网搜索 | `GET /api/v1/content/global_search` | 补充站外权威来源做对照 |
| 知乎热榜 | `GET /api/v1/content/hot_list` | 一键从真实热点进入体验 |
| 问题回答摘要 | `GET /api/v1/content/question_answers` | 粘贴知乎问题链接时读取真实回答 |
| 知乎直答 | `POST /v1/chat/completions` | 按该答主的人格（voice）生成回答；也用于抽取人格四要素与互相回应 |
| 问题推荐 | `GET /api/v1/user/question_recommendations` | 从真实用户画像找到「该被问的人」 |
| 黑客松故事/知识 | `api.zhihu.com/km-indep-home/hackathon/v2/*` | **实测 401**（依赖浏览器登录票据），已接入但当前不可用，见下方说明 |
| 知乎登录（OAuth） | `openapi.zhihu.com/authorize` + `/user` | 登录与用户基础信息（加分项） |

### 重要的事实边界（如实说明）

**边界一：平台没有发布接口。** 经全量审计，知乎开放平台不提供写入/发布接口，
全部 54 个文档条目均为只读。因此本产品**不承诺一键发布**，也不做任何「预填」暗示：
只把整理好的正文（含来源归属）放到可复制的面板里，由用户自己到知乎对应问题下发布。
产品内的所有来源链接、作者名原样保留。

**边界二：有一个接口我们接了但用不了。** 官方指南提到的
`api.zhihu.com/km-indep-home/hackathon/v2/{story,knowledge}/list` 是知乎站内页面接口，
实测无论是否携带 Access Secret 都返回 `401 ERR_PARSE_LOGIN_TICKET`（依赖浏览器登录票据）。
我们在页面上如实标注为 401，不替换成别的数据假装它可用。

**边界三：参数名踩坑已记录。** 搜索类接口的条数参数是 `Count` 而不是 `Limit`；
传错不会报错，只会静默按默认值返回 10 条。本项目已按官方字段名修正并写入审计文档。

## 5. 与知乎社区生态的契合点

1. **证据回流**：每条分身回答都带真实的知乎链接与作者名，用户顺着链接回到知乎阅读原文。
2. **激活沉默的分享者**：缺口派单指向真实知乎用户，把「愿意分享但没被问对」的人重新激活。
3. **减少重复提问**：先让 AI 把问题问清楚，用户带回去的是更有信息增量的问题。
4. **提升回答质量**：真人只回答他真正擅长的那一块，而不是被泛泛的问题劝退。
5. **合规优先**：不刷量、不批量调用；所有内容保留归属；凭证严格留在服务端。
   预置答主的人格语料为**本地一次性取样**（脚本与原始语料均不入公开仓库），人格文件只存特征与短引用。

**知乎在这个产品里不是数据源，而是循环本身。**

## 6. 对社区用户的实际价值

| 对象 | 价值 |
|---|---|
| 提问者 | 从「看排序」升级为「看结构」：知道有哪些立场、各自代价、以及自己还缺什么信息 |
| 有经验的人 | 被问到一个「正好是我能答」的问题，而不是泛泛求助 |
| 知乎平台 | 更多有信息增量的回答，更少重复提问；内容带来源回流 |
| 社区生态 | 把 AI 的效率与真人的可信度接起来，而不是用 AI 替代真人 |
