# PRD · 二号知乎（Human Mesh）

> 最后更新：2026-09-14 · 赛道：**知识炼金场｜社区 × 学习**（主）/ 灵魂匹配局（交叉）

## 一、一句话

**把一个问题，交给知乎上你想听的几位答主先答一遍——按他们各自真实的领域、立场和说话方式——再看他们共同缺了什么，把缺的那一块交给真实的人。**

评价标准是「像这个人」>「答案完美」：同一个问题换三位答主，遮住名字也该看得出不是同一个人写的。

## 二、要解决的三个真问题

1. **一个人问问题，只能得到一个视角。**
   同一个问题在知乎上往往有几十个高质量回答，观点互相冲突。用户看到的是排序，不是结构——
   没人告诉他「这些回答在争什么、分歧点到底在哪、他们共同没回答的是什么」。

2. **AI 的回答很快，但不可信；真人的回答可信，但很慢。**
   纯 AI 问答缺一手经验，纯社区检索缺结构。缺的是把两者接起来的那一步。

3. **有价值的亲身经历，没有被问对的问题触发。**
   知乎上愿意分享的人很多，但他们不会主动回答一个没人问好的问题。
   问题的**提法**决定了能不能把经验钓出来。

## 三、目标用户

| 用户 | 场景 | 他要什么 |
|---|---|---|
| **提问者**（主） | 面临真实决策：转行、择校、选品、看病、育儿、创业 | 不是「标准答案」，而是「有哪些立场、各自代价是什么、我还缺什么信息」 |
| **有经验的人**（副） | 在某个领域真的踩过坑 | 被问到一个「正好是我能答」的好问题，而不是泛泛的求助 |
| 社区 | 知乎内容生态 | 更少重复提问、更多有信息增量的回答 |

## 四、核心闭环（Demo 必须完整走通一遍）

```
① 提问          用户输入真实问题（或粘贴知乎问题链接 / 从热榜挑）
      ↓
② 选人          ★ 指定想听谁回答（多选）；也可以交给看山按问题推荐
      ↓
③ 取证据        每位答主用领域关键词检索知乎真实回答 → 拿到带作者和链接的证据
      ↓
④ 作答          基于证据、按该答主的 voice 生成回答草稿（字数区间也由人格决定）
      ↓
⑤ 加人          继续邀请新答主加入，只生成这一位，不重跑已有分身
      ↓
⑥ 互怼          一轮互相回应：找出最尖锐的分歧，让双方各回一段（不循环）
      ↓
⑦ 找缺口        ★ 对比所有回答，找出「所有人都没说到、但回答这个问题必须知道」的那一块
      ↓
⑧ 派单          缺口 → 需要什么样的真人 → 候选真人（来自知乎公开数据）
      ↓
⑨ 接管          真人补充 → 内容标记为「真人补充」→ 并入最终稿
      ↓
⑩ 带走          导出 / 复制成知乎回答格式，用户自己发布到知乎
```

**两个创新点。** 第 ② 步：不是让 AI 换六种语气，而是让**具体的人**各自作答（依赖真实人格蒸馏）。
第 ⑦ 步「找缺口」：前几步市面上有类似产品；把「一群分身各自答完，然后系统指出它们共同的盲区」
做成可见的交互，是新的，也是评审看到的最不可替代的一步。

## 五、看山（刘看山）在产品里的角色

看山不是装饰，是**主持人**：

- **主持路由**：召集分身时说「我找了 4 个人来答这个问题」，并说明为什么是他们。
- **主持缺口**：指着空白说「这里没人能答，需要真人」。
- **主持接管**：真人补充后，看山把这一块拼回整体。
- **情绪状态**：思考（路由中）、召集（分身出现）、困惑（发现缺口）、满意（缺口被补上）。

这条情绪线让抽象流程变成可感知的角色动画，也是设计感的来源（评审权重 10%）。

## 六、知乎能力映射（每一项都必须用得上）

| 环节 | 知乎能力 | 接口 | 为什么必须用它 |
|---|---|---|---|
| ② 路由 | — | 本地纯函数 | 保证可解释、可复现、零额度消耗 |
| ③ 取证据 | 知乎搜索 | `GET /api/v1/content/zhihu_search` | 每位答主拿到**真实**的知乎回答，带作者/链接/赞同数 |
| ③ 补证据 | 全网搜索 | `GET /api/v1/content/global_search` | 补充站外权威来源，做观点对照 |
| ① 入口 | 知乎热榜 | `GET /api/v1/content/hot_list` | 一键从真实热点进入体验，降低冷启动门槛 |
| ③ 深挖 | 问题回答摘要 | `GET /api/v1/content/question_answers` | 用户粘贴知乎问题链接时，读取该问题下的真实回答摘要 |
| ④ 作答 | 知乎直答 | `POST /v1/chat/completions` | 按该答主的人格（voice）组织回答；也用于抽取人格四要素、互相回应。**仅关键节点调用** |
| ⑥ 派单 | 问题推荐 / 创作能力 | `/api/v1/user/question_recommendations` | 从真实用户画像找「该被问的人」 |
| 备选素材 | 知乎故事 / 知识 | `api.zhihu.com/km-indep-home/hackathon/v2/*` | 无鉴权，可作为示例问题的种子内容 |
| 加分 | OAuth 登录 | `openapi.zhihu.com/authorize` + `/user` | 登录数计入最佳人气奖评定 |

**额度纪律**（2026-09-14 实测）：搜索 5000/天、直答 5000/天、热榜 100/天、用户数据 10000/天。
单次体验 ≤7 次直答（3 位答主 + 1 次邀请 + 1 轮互相回应 = 6 次）。全部走 [architecture.md](architecture.md) 定义的缓存层，同一问题 30 分钟内不重复消耗。

## 七、为什么必须用 AI（评审必问）

- 路由：需要理解问题的**语义类型**（判断型 / 方法型 / 解释型），不是关键词匹配。
- 作答：需要把多条**互相矛盾**的真实回答，压缩成一个立场一致的视角草稿。
- **找缺口：需要跨多个回答做「共同缺失」的推理，这是纯检索做不到的。**
- 派单：需要把缺口翻译成「什么样的人能答」。

## 八、为什么必须在知乎生态里（评审必问）

- 证据来自知乎真实回答，作者和链接原样保留 → 用户顺着链接回到知乎，形成回流。
- 缺口派单指向真实知乎用户 → 把社区里的「愿意分享的人」重新激活。
- 最终稿导出成知乎回答格式 → 用户带回知乎发布。
- **知乎不是数据源，是这个产品的循环本身。**

## 九、明确不做什么

| 不做 | 原因 |
|---|---|
| 一键发布到知乎 | 开放平台无写入接口（见 [publish-path.md](publish-path.md)） |
| 批量爬取 / 滥用用户数据 | 违反平台红线。预置答主语料仅**本地一次性取样**，脚本与原始语料不入公开仓库，人格文件只存特征与短引用 |
| 用 AI 冒充真人回答 | 违反原创与合规要求 |
| 无限轮询热榜 | 100/天额度，且平台明令禁止 |
| 复制参考项目素材 | 素材归 xAI，仅可学习架构 |

## 十、验收标准（Demo）

- [ ] 输入一个问题，10 秒内进入「选答主」，看到多位答主带着**真实知乎链接**出现
- [ ] 每个答主显示领域、立场、语癖、不装懂边界、命中的证据、路由理由
- [ ] **同问题换 3 位答主，遮住名字能明显分辨是三个人**（最高优先级）
- [ ] 缺口被明确标出，并说明「为什么这是缺口」「需要什么样的真人」
- [ ] 至少能演示一次「真人补充 → 缺口被填上」的状态变化
- [ ] 看山在整条流程中有对应的状态变化，动效流畅不掉帧
- [ ] 断网 / 额度耗尽 / 空结果都有真实提示，不是白屏
- [ ] 计划书、仓库、Demo 三者描述一致，无夸大
